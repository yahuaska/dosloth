# План: единая таблица прерываний из вызываемых объектов

## Зачем
Сейчас `INT n` вызывает Python-функцию из `cpu.int_handlers`, а `INT 21h AH=25h/35h` пишет и читает байты по `0000:n*4`, и эти записи ни на что не влияют. Нужно, чтобы:
- программа могла поставить свой обработчик (`AH=25h`), и `INT n` реально прыгал в её код;
- Python-обработчики и код программы лежали в одной таблице и вызывались одинаково.

## Идея (вариант A)
Одна таблица `cpu.vectors: n -> callable(cpu)`. `INT n` всегда делает `vectors[n](cpu)`.
- Python-обработчик: обычная функция, как `int21`.
- Код программы: объект `GuestHandler(seg, off)` с `__call__`, который делает то, что делает настоящий `INT`: кладёт в стек флаги, CS, IP, сбрасывает IF/TF и прыгает на `seg:off`.

## Шаги (по одному, каждый запускает на одну программу больше)
1. **`IRET` (`CF`)**: достать из стека IP, CS, флаги. Без него вернуться из обработчика программы нельзя.
2. **`GuestHandler`** и переименование `int_handlers` в `vectors` (функции из `dos.py` остаются как есть).
3. **`AH=25h`** кладёт в таблицу `GuestHandler(DS, DX)`.
4. **`AH=35h`**: для `GuestHandler` вернуть его `seg:off`. Для Python-обработчика пока вернуть `0000:0000`.
5. **`PUSHF`/`POPF` (`9C`/`9D`)**: нужны, когда программа вызывает старый обработчик как `pushf` + `call far`.

Брать шаги по мере того, как их требует очередная программа (сейчас `esetup.exe` только сохраняет вектор INT 0).

## Что решить, когда понадобится
- **Два источника правды.** Таблица-словарь и байты по `0000:n*4` расходятся. Если программа читает таблицу напрямую (`les bx,[0:n*4]`), она ничего не увидит. Тогда переходим на вариант B.
- **Цепочка к Python-обработчику.** Если программа получила адрес через `AH=35h` и вызывает его (`call far`), нужен адрес, на котором `step()` вызовет Python-функцию. Варианты: фиктивные адреса `F000:nn` и проверка в `step()`, либо заглушки в памяти из особого опкода `PYCALL n` + `IRET`.

## Вариант B (если A упрётся)
Таблица в памяти по `0000:n*4` — единственная правда, как в железе. `INT n` читает её и прыгает. Python-обработчики прячутся за заглушками в памяти (`PYCALL n; IRET`), а в таблице лежит адрес заглушки. Тогда `AH=35h` всегда возвращает настоящий адрес, а `GuestHandler` не нужен.

## Не делаем
Аппаратные прерывания (таймер, клавиатура), IF/TF как настоящие флаги, пока ни одна программа их не требует.

# План: конфиг окружения и файловая система (записано 2026-10-13, обновлено 2026-10-19)

## Зачем
`esetup.exe` дошёл до файловых функций (`INT 21h AH=43h`, перед этим `3Eh`) и до перебора дисков (`0Eh`, `19h`, `44h/08h`). Диски и их свойства сейчас зашиты константами в `dos.py` (`DRIVES`, `REMOVABLE_DRIVES`, `DEFAULT_DRIVE`). Нужен конфиг, который описывает диски и то, что в них вставлено, чтобы программа видела настоящие файлы.

## Принятые решения
1. **Формат: TOML** (`tomllib` из стандартной библиотеки, Python 3.12).
2. **Относительные пути в конфиге считаются от каталога конфига.** (Для встроенного конфига без `-c` их база — текущий каталог процесса.)
3. **Дисковод и носитель описываются отдельно.** `[disks.X]` — свойства устройства (`removable`), `[mounts]` — что в нём лежит. Нет записи в `mounts` = носителя нет (пустой дисковод). Это допустимо только для сменного диска; у несменного нет монтирования — **ошибка при разборе конфига**. (В TOML нет `null`, поэтому «пусто» = записи нет.)
4. **Виды монтирования** с явным `type`: `dir` (каталог хоста, обязателен `path`) и `tmpfs` (файловая система в памяти, при выходе пропадает). Overlay или copy-on-write — потом.
5. **`readonly`** — свойство монтирования (носителя), по умолчанию `false`.
6. **`cwd`** — начальный диск и каталог **внутри DOS** (`cwd = 'C:\SETUP'`, литеральная строка TOML, без экранирования). Заменяет прежний `default`.
7. **Программа в командной строке задаётся путём DOS**, не путём хоста: `esetup.exe`, `C:\ESETUP.EXE`, `setup\esetup.exe` (допустим и `/`). Он разрешается через монтирования и текущий каталог, как это делает DOS. Чтобы запустить файл с хоста, его каталог монтируют в диск и выставляют туда `cwd`.
8. **Ключ `-c <файл>`** передаёт конфиг. Без него встроенный: A:, B: (сменные, пусто), C: (несменный, `dir` = текущий каталог процесса), D: (сменный, пусто), `cwd = 'C:\'`. Так `python -m mydos esetup.exe` в каталоге с программой работает и без конфига.
9. **Файлы ищутся без учёта регистра** (DOS нечувствителен к регистру, Linux чувствителен): путь разбирается по компонентам.

## Формат (пример)
```toml
cwd = 'C:\'                       # начальный диск и каталог внутри DOS

[disks.A]
removable = true                  # в mounts нет A: дисковод без дискеты
[disks.B]
removable = true
[disks.C]
removable = false
[disks.D]
removable = true

[mounts]
C = { type = "dir", path = "." }                       # от каталога конфига
D = { type = "dir", path = "/tmp", readonly = true }   # «компакт-диск»
B = { type = "tmpfs" }                                  # дискета в памяти
```
(Файл `samples/config.yaml` — набросок в YAML; переписать как TOML.)

## Правила разбора (любая ошибка: понятное сообщение и выход, без запуска)
- имя диска — одна латинская буква (регистр не важен), хранится заглавной; хотя бы один диск;
- `removable` обязателен (bool);
- ключи `mounts` должны быть среди `disks`; у несменного диска монтирование обязательно;
- `type` — только `dir` или `tmpfs`; у `dir` обязателен `path` (каталог должен существовать), у `tmpfs` его быть не должно; другие ключи (кроме `readonly`) — ошибка;
- `cwd`: буква существующего диска **с носителем** и каталог, который на нём есть;
- без `cwd`: `C:\`, если C: смонтирован, иначе корень первого смонтированного диска;
- неизвестные ключи на любом уровне — ошибка (ловит опечатки).

## Что меняется в существующем коде
- **`mydos/__main__.py`**: аргумент `program` теперь путь DOS; ключ `-c`; запуск через монтирования.
- **`mydos/psp.py`**: имя программы в блоке окружения строится из её DOS-пути (`C:\ESETUP.EXE`), а не склеивается из имени файла.
- **`mydos/dump.py`**: дамп падения кладётся рядом с запущенным файлом на хосте (путь хоста берётся из разрешённого DOS-пути).
- **`tests/test_psp.py`**: запускает `.com` по абсолютным путям во временных каталогах; перевести на конфиг, который монтирует этот каталог.
- **`AGENTS.md`**: примеры запуска и описание конфига; пример положить в корень как `config.example.toml` (каталог `samples/` в `.gitignore`).

## Шаги
1. **`mydos/config.py`**: разбор и проверка TOML (диски, монтирования, `cwd`), встроенный конфиг; тесты на каждое правило и на относительные пути. Файловая система на этом шаге ещё не нужна: монтирование хранится как описание.
2. **Замена констант в `dos.py`** данными из `Config` (`DRIVES`, `REMOVABLE_DRIVES`, текущий диск), `install(cpu, config)`. `AH=0Eh` возвращает «наибольший номер диска + 1» (в конфиге бывают пропуски). Ключ `-c`.
3. **Файловые системы с общим интерфейсом**: `HostDir` (каталог хоста: поиск без учёта регистра, `readonly`, выход выше корня запрещён) и `MemFs` (дерево в памяти для `tmpfs`). Перевод `(диск, путь DOS, текущий каталог диска)` → объект файловой системы. Текущий каталог для каждого диска в `DosState` (начальный из `cwd`). Диск без носителя даёт ошибку 15h. Запуск программы по DOS-пути; переделка PSP, дампа и тестов (см. выше).
4. **Файловые функции по очереди, как их требует программа**: `43h` (атрибуты), `3Dh` открыть, `3Fh` читать, `42h` перемотка, `3Ch` создать, `40h` запись в файл, `4Eh/4Fh` поиск, `47h`/`3Bh` каталоги, `36h` свободное место, `1Ah` DTA.

## Открытое
- Overlay / copy-on-write над каталогом хоста (чтение с хоста, запись в память).
- Длинные имена хоста: скрывать от программы или сокращать до `ИМЯ~1`; два файла, различающиеся только регистром.
- Запуск по имени без расширения (DOS пробует `.COM`, потом `.EXE`) и каталог `PATH`.
- ~~Ключ `type` у диска (`floppy`, `hdd`, `cdrom`) вместо `removable`~~ — сделано (2026-10-21): `removable` остаётся старой записью; у `cdrom` носитель всегда `readonly`, `tmpfs` нельзя; INT 2Fh отвечает за MSCDEX.

# План: игра на DOS/4GW — защищённый режим 386 (записано 2026-10-23)

## Зачем
Основные программы X-COM: Apocalypse (`ufoexe\ufo2p.exe`, `tacexe\tacp.exe`, `smkp.exe`) — 32-битные, собраны Watcom и упакованы вместе с расширителем DOS/4GW (в файлах строки `DOS/4G`, `Rational`, `WATCOM`; в `ufo2p.exe` похоже на LE-модуль для 386 из двух объектов, код и данные, около 1,2 МБ). Оболочка `xcomapoc.exe`, установка (`install.exe`), настройка (`esetup.exe`, `gsetup.exe`) — обычный реальный режим. Пока мы делаем реальный режим; защищённый режим — следующий большой этап.

## Три способа запустить программу на DOS/4GW
1. **Честный.** Эмулировать защищённый режим 386 целиком (дескрипторы, GDT/LDT/IDT, привилегии, переключение режимов, исключения, V86 или обратные вызовы реального режима) и запускать настоящий расширитель из файла.
2. **С упрощением (выбран).** Своим загрузчиком разобрать LE-модуль (объекты, таблица страниц, фиксапы, точка входа, стек), запустить его в плоской 32-битной модели; услуги DOS/4GW и DPMI (`INT 21h`, `INT 31h`) сделать функциями на Python. Расширителя в памяти нет: нет заглушки, переключения режимов, таблиц GDT/IDT в памяти, V86. Подходит программам, которые пользуются только документированным интерфейсом DOS/4GW и DPMI.
3. **На процессоре хоста** (как `dosemu`: `modify_ldt`, сигналы вместо прерываний). Не берём: нужен код вне Python, нет воспроизводимости, работает только на Linux x86.

## Решение
Способ 2. Способ 1 возвращаем, только если встретится программа, которая сама переключает режимы (другой расширитель, свой переход в защищённый режим). Способ 2 экономит примерно треть работы и даёт проверяемый результат по одному вызову за раз, как и до сих пор.

## Что отпадает при способе 2
Защищённый режим как механизм (GDT/IDT в памяти, уровни привилегий, `lmsw`, `mov cr0`, исключения процессора), сам расширитель DOS/4GW, V86.

## Что остаётся в любом случае
- **Набор команд 386.** 32-битные регистры (`EAX`…), префиксы `66h` и `67h`, адресация со SIB, `movzx`/`movsx`, `setcc`, `bt*`, `shld`/`shrd`, `imul r, r/m`, 32-битные строковые операции, условные переходы `0F 8x` со смещением 32 бита. Основной объём работы, общий для обоих способов.
- **Минимальные сегменты:** таблица «селектор → база, предел» в Python.
- **Услуги DPMI и DOS/4GW** (пара десятков функций): выделение памяти и дескрипторов, `INT 31h AX=0002` (сегмент реального режима в селектор), `AX=0300` (вызвать прерывание реального режима), векторы прерываний защищённого режима, блокировка памяти.
- **Аппаратные прерывания:** таймер (`IRQ0`) через PIT и PIC, клавиатура (`IRQ1`). Игры вешают на них свои обработчики. Сейчас у нас только `INT n` программы.
- **Звук:** игра сама загружает 32-битные драйверы HMI (`hmidrv.386`, `hmimdrv.386`), которые работают с портами звуковой карты. Сначала «нет звука» в настройке, потом эмуляция карты, если захочется.
- **Видео:** режимы с одним байтом на пиксель (13h или VESA); у нас пока только 16-цветная планарная модель. Что именно нужно, покажет трасса.
- **Память:** XMS или то, что даёт DPMI; `INT 15h` (размер расширенной памяти); `AH=48h`/`49h` и цепочка блоков.

## Порядок
0. Дожать реальный режим: установщик (`install.exe`), настройка, настоящий `xcom3.cfg`, запуск `xcomapoc.exe` до места, где он передаёт управление `ufo2p.exe`.
1. Ядро 386 как расширение текущего процессора: общий код с 16-битным режимом, режим операнда и адреса (16 или 32) как состояние, тесты по независимому эталону (как для остальных команд), потом проверка на программе, которая не переключает режимов.
2. Загрузчик LE и DPMI на Python; плоская модель, минимальная таблица селекторов.
3. Прерывания таймера и клавиатуры (PIT/PIC), доставка между командами.
4. Звук и видео 256 цветов по необходимости.

## Открытое
- Уточнить разбор «bound»-файла: где в `ufo2p.exe` начинается LE-модуль и как отличить его от расширителя (заглушка из 62 КБ; в файле несколько совпадений с `LE`).
- Нужен ли VESA и что именно запрашивает игра (`INT 10h AX=4F00h`, `4F02h`).
- Понадобятся ли сегменты `FS` и `GS` и команды с управляющими регистрами (`mov cr0`): покажет трасса.
